# llama-vscode-chat — агентные инструкции

## Рабочий процесс: оркестратор и исполнитель

Если основная модель чата — Codex GPT‑Sol или Claude Opus, задача решается в паре.

- **Оркестратор (основная модель).** Изучает задачу и код, составляет план,
  делит его на шаги, ставит задачи исполнителю, проверяет каждый результат и
  отвечает пользователю. За оркестратором остаются архитектурные решения, код с
  риском для безопасности, финальная проверка (`npm run compile`,
  `npm run lint`, `npm test`), версия, CHANGELOG, сборка и установка VSIX,
  коммиты и пуши (только по просьбе пользователя).
- **Исполнитель — DeepSeek Flash (провайдер DeepSeek).** Всегда модель
  семейства Flash, а не Pro, без привязки к номеру версии: модель DeepSeek, в id
  которой есть `flash`. Получает шаги плана: правки кода, тесты, поиск по коду,
  рутинные проверки. Flash принимает изображения.
- **Тул субагента зависит от чата.** Пока работают оба чата, имена разные:
  - Copilot Chat — `runSubagent`, `model` из списка в его описании (сейчас
    `deepseek-flash (DeepSeek) (llamacpp)`);
  - бридж-чат (AI Agent Bridge Chat) — `subagent`, `model` из списка в его
    описании, а под Coco — из описания параметра `model` (сейчас
    `deepseek-flash (DeepSeek)`; вариант с ` (llamacpp)` тоже принимается).

  Остальные тулы тоже называются по-разному (например, `llamacpp_coco_run_in_terminal`
  в Copilot Chat и `run_in_terminal` в бридж-чате): бери имена из списка тулов
  текущего чата. В бридж-чате выключенные тулы видны через `list_tools`,
  включить их можно через `request_tools`.

### Как ставить задачу исполнителю

Субагент не видит переписку и не помнит прошлые вызовы, поэтому каждый промпт
самодостаточен:

1. Цель шага и его место в общем плане (1–2 фразы).
2. Файлы, которые можно менять; остальные — только читать.
3. Нужный контекст: сигнатуры, выдержки кода, принятые решения — чтобы
   исполнитель не искал их заново.
4. Правила проекта: сохранять окончания строк файла (в `src/` — CRLF) и UTF-8,
   не добавлять зависимости, не трогать версию, CHANGELOG, VSIX и git.
5. Критерий готовности и проверка: минимум `npm run compile` и `npm run lint`.
6. Формат ответа: изменённые файлы, суть правок, результаты проверок, что не
   сделано и почему, открытые вопросы.

### Проверка результата

- Результат не принимается на слово: оркестратор читает изменённые места,
  смотрит ошибки компиляции и при необходимости запускает тесты.
- Замечания отправляются новым вызовом с конкретным списком исправлений.
- Независимые шаги, которые меняют разные файлы, можно запускать параллельно;
  шаги с общими файлами — по очереди.
- Шаги плана ведутся в todo-списке.

### Когда не делегировать

- Правка в одну-две строки, документация, ответ на вопрос — оркестратор делает
  сам, если постановка задачи дороже самой работы.
- DeepSeek недоступен (баланс, лимит, ошибка API): оркестратор выполняет шаг
  сам и сообщает об этом. Другую модель исполнителем без согласования не
  подставлять.
- Для крупной задачи план (этапы, решения, риски, открытые вопросы) сначала
  согласуется с пользователем, реализация начинается после согласования.

### Процесс экспериментальный

- Если субагенту не хватает возможностей (нет нужного тула, обрезается вывод,
  отклоняется модель, теряется контекст), это дефект моста: его чинят в
  расширении, чтобы субагенты работали полноценно, а не обходят молча.
- Проблемы процесса (качество работы исполнителя, лишние переделки, стоимость)
  оркестратор сообщает пользователю. Если процесс окажется плохим, от него
  откажутся — решение за пользователем.

## Сборка и установка расширения (обязательный порядок)

Никогда не копируй папки вручную в `~/.vscode/extensions/` и не правь `extensions.json` руками.
Расширение устанавливается из `.vsix` (source: vsix), VS Code сам обновляет `extensions.json` и чистит `.obsolete`.

**Устанавливай сразу, не спрашивая.** `npm run package` и следующий за ним
`code --install-extension … --force` — одна операция: как только VSIX собран,
он немедленно ставится в VS Code, версия проверяется по `extensions.json`, и в
ответе указывается, что нужен Reload Window. Не жди отдельной команды «установи»
и не предлагай установить вручную через UI. Исключение — только явная просьба
не устанавливать.

```bash
# 1. Компиляция TypeScript
npm run compile

# 2. Сборка .vsix пакета (включает prepublish: clean + compile)
npm run package
# → llama-vscode-chat-{version}.vsix

# 3. Установка через code CLI
code --install-extension llama-vscode-chat-{version}.vsix

# 4. Перезагрузка окна
# Ctrl+Shift+P → Developer: Reload Window
```

### Что делает `npm run package`
- `vsce package` — собирает расширение в `.vsix`
- Автоматически выполняет `npm run vscode:prepublish` (clean + compile)
- Упаковывает только файлы, перечисленные в `.vscodeignore`

### Проверка после установки
```bash
node -e "
const fs = require('fs');
const dir = process.env.USERPROFILE + '/.vscode/extensions';
const json = JSON.parse(fs.readFileSync(dir + '/extensions.json', 'utf8'));
const ext = json.find(e => e.identifier?.id === 'mrlordcat.llama-vscode-chat');
console.log('version:', ext?.version, 'source:', ext?.metadata?.source);
"
```
Ожидаемый результат: `version: {текущая} source: vsix`

## Правило версионирования

### Dev-патчи (третья цифра): `1.8.5`, `1.8.24`, `1.9.1`, `1.9.18` и т.д.
**Инкрементировать ТОЛЬКО третью цифру (patch).**
Вторую цифру (minor: `1.9.0`) **НЕ поднимать** без явной команды пользователя.
Причина: может пройти много итераций исправлений до стабильного состояния.

Версию поднимать только `npm version 1.20.19 --no-git-tag-version` (меняет
`package.json` и `package-lock.json` в UTF-8). Не переписывать `package.json`
через `Get-Content`/`Set-Content` Windows PowerShell 5.1: он читает UTF-8 как
ANSI, и каждая перезапись умножает испорченные символы. `npm run check:metadata`
такую порчу находит.

Dev-патчи **не тэгаются** и не публикуются без явной команды пользователя.
По команде «выпустить промежуточный релиз» патч выпускается так же, как
стабильный (см. «Релиз патча»), и updater предлагает его пользователям.

### Стабильные релизы (вторая цифра): `1.9.0`, `1.10.0`, `1.11.0`
Когда код достигает стабильного состояния — пользователь даёт явную команду
«выпустить стабильную версию». Тогда:
1. Версия в `package.json` поднимается до следующей minor (например `1.9.0`)
2. Создаётся аннотированный git-тег: `git tag -a v1.9.0 -m "Stable release 1.9.0"`
3. Тег пушится: `git push origin v1.9.0`
4. Собирается `.vsix` и прикрепляется к GitHub Release

Автоматизировано скриптом `scripts/stable-release.sh`.

### Релиз патча (по явной команде)
```bash
bash scripts/stable-release.sh 1.20.2
```
Тег `v*` запускает workflow Release: lint + тесты + `npm run package`,
затем GitHub Release с платформенными VSIX для Windows и Linux. Описание релиза
берётся из `docs/RELEASE_NOTES.md` (первая строка `# AI Agent Bridge 1.20.2`),
поэтому его и `CHANGELOG.md` обновляют ДО тега. Патчи тэгуются только по явной
команде пользователя.

### Хранение релизов
После публикации workflow запускает `scripts/prune-releases.mjs --github` и
удаляет старые GitHub Releases вместе с тегами. Остаются:
- `x.y.0` трёх последних линий (например `1.20.0`, `1.19.0`, `1.18.0`);
- два последних патча только последней линии (`1.20.2`, `1.20.5`; после
  `1.20.6` удаляется `1.20.2`, после `1.21.0` — все патчи `1.20.x`).

Теги не вида `vX.Y.Z` не трогаются. Чистка запускается только после успешной
публикации текущего релиза. То же правило для локальных VSIX и тегов —
`npm run prune:local`; установленные расширения в `~/.vscode/extensions`
чистит сам VS Code.

### Откат к стабильной версии
```bash
git checkout v1.9.0
npm run package
code --install-extension llama-vscode-chat-1.9.0.vsix
```
Это даёт гарантированно работающую версию — даже если dev-патчи что-то сломали.
