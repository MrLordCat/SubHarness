# План работ: агенты, самоочистка контекста, локальные модели

Цель: агенты в чате SubHarness работают быстрее и качественнее, чат сам держит контекст компактным и актуальным
(без необходимости начинать новый чат), локальные модели (окно 256k и больше) снова полезны.

Нумерация продолжает линию 2.0. Порядок: сначала этап 1 — то, что ускорит дальнейшую работу. Он выпущен
промежуточным релизом **2.0.9**; после **Developer: Reload Window** работа продолжается уже с новыми
возможностями. Этапы 2–4 проверяются тестами без сборки, одна сборка в конце (этапы 1–3 вышли в 2.0.9–2.1.0, дальше линия 2.1.x). Релиз — по
просьбе пользователя.

Правила исполнения: шаги делают субагенты (Luna или DeepSeek Flash — мелкие, Terra — крупные), оркестратор проверяет каждый дифф;
каждый этап закрывается `npm run compile`, `npm run lint`, полным `npm test`, записью в CHANGELOG и документацией.

## Этап 1. Скорость работы агентов (выпущен в 2.0.9)

- [x] **1.1 Параллельные субагенты.** Несколько вызовов `subagent` в одном ответе выполняются одновременно (не
  больше 3), а не по очереди, как сейчас (`agent-loop.ts`, цепочка `subagents.then`). У каждого свои терминалы и
  своя карточка; изменения файлов идут в тот же Keep/Undo хода. Пересечение по файлам не блокируется, но гайд
  велит запускать параллельно только шаги с разными файлами.
- [x] **1.2 Фоновые субагенты.** `subagent` с `background: true` сразу возвращает id, основной агент работает
  дальше. Новый инструмент `wait_subagents` ждёт отчёты (всех или перечисленных id, с таймаутом) и возвращает их.
  Ход длится, пока работают его фоновые субагенты (так Keep/Undo, подтверждения, карточки и Stop работают как
  обычно); несобранные отчёты приходят агенту следующим автоматическим сообщением через очередь. Готовность
  фонового субагента отмечается строкой в ближайшем результате инструмента.
- [x] **1.3 Отчёт субагента с изменениями.** К тексту отчёта хост добавляет список файлов, которые записали
  инструменты субагента, с числом добавленных и удалённых строк относительно состояния до его запуска. Основному
  агенту не нужно собирать `git diff` самому.
- [x] **1.4 Инструмент `run_checks`.** Запускает проверки проекта без терминала и возвращает сжатый итог: статус,
  число пройденных/упавших, имена упавших тестов и суть ошибок (TypeScript, ESLint, mocha), путь к полному логу.
  Команды: из `.subharness/checks.json`, иначе из скриптов `package.json` (`compile`, `lint`, `test`).
  Таймаут, Stop прерывает процесс.
- [x] **1.5 Диагностика после правки.** `replace_string_in_file`, `multi_replace_string_in_file` и `create_file`
  ждут обновления диагностик (до ~1,5 с) и дописывают в результат новые ошибки в изменённых файлах (не больше 10).
- [x] **1.6 Retry видит прерванную попытку.** Сейчас Claude возобновляет сессию с последнего стабильного ответа
  (`stableAssistantMessageId`), и работа прерванной попытки до модели не доходит. Продолжение после обрыва несёт
  сводку попытки: вызванные инструменты с ключевыми аргументами и коротким итогом, изменённые файлы из Keep/Undo,
  todo-список, последний текст. Проверить и для Codex, Cursor, Coco, HTTP.
- [x] **1.7 Терминал.** Команда, которая молчит и ждёт ввода (`(Y/n)`, `Press Enter`, `password:`), возвращается
  раньше со статусом «ждёт ввода». Строки прогресса, перерисованные через `\r`, и спиннеры схлопываются до
  последнего состояния. Ошибка «Unknown terminal ID» объясняет причину (закрыт, перезагрузка окна) и перечисляет
  живые терминалы.
- [x] **1.8 Гайд в системном промпте** описывает параллельных и фоновых субагентов, `wait_subagents`, `run_checks`
  и ревью изменений дешёвым субагентом перед ответом для нетривиальных правок.

## Этап 1А. Лимиты и подписки (до этапа 2, решение пользователя 2026-11-25)

Порядок: 1А.1 → 1А.2 и 1А.3 → этап 2 → остальное.

- [x] **1А.1 Автопродолжение и время сброса** (сделано в 2.0.12). Найденные причины:
  - Текст лимита с датой не разбирается. Claude пишет `You've hit your weekly limit · resets Nov 28, 4pm
    (Europe/Tallinn)` (сброс дальше 24 ч, формат CLI `b$`), Codex — `Try again at Nov 28th, 2026 4:12 PM.`
    `CLOCK_PATTERN` в `limit-errors.ts` ждёт цифру сразу после `resets`/`try again at`, поэтому время сброса
    пропадает. Голое время (`resets 4pm`) у недельного окна превращается в ближайшие 4pm, отсюда «через N ч»
    вместо дней. Метки CLI `session limit`, `Opus limit`, `Sonnet limit` не дают окна.
  - Свой отчёт провайдера не используется. У Claude `rate_limit_event` несёт `rateLimitType` и `resetsAt`, но
    `app-server-client.ts` отбрасывает тип. У Codex `resolveCodexLimitGate` берёт первое окно на 100% (5h), а не
    то, что сбросится последним.
  - Ожидание длиннее суток показывается часами (`in 52 h`); в тексте уведомления — только `HH:MM` без даты.
  - Автопродолжение режется горизонтом 6 ч. Решение: у недельного лимита карточка показывает верную дату, галочка
    есть, но выключена; включить её можно вручную.
- [x] **1А.2 Две подписки Claude** (сделано в 2.0.12; вживую с двумя аккаунтами не проверено) — как у Codex (2.0.11). Второй аккаунт — свой `CLAUDE_CONFIG_DIR`, в котором CLI
  хранит `.credentials.json`, `.claude.json` и сессии. Вход — `claude auth login --claudeai` с этой переменной.
  Настройка аккаунтов, квоты обеих подписок, модели в пикере один раз. Субагент выбирает подписку при запуске:
  активная, затем по порядку, исчерпанная пропускается. Открытый субагент переезжает на другую подписку с
  историей. Сессии SDK не переносятся между аккаунтами: переезд — новая сессия с replay, как при смене провайдера.
- [x] **1А.3 Лимит одной подписки в основном чате** (сделано в 2.0.12) (вместо 3.1, для Claude и Codex). Карточка лимита предлагает
  кнопку «Продолжить на Claude 2 / Codex 2», если у другой подписки той же модели есть запас; по нажатию ответ
  продолжается, как по Retry, на той же модели другой подписки.

## Этап 2. Самоочистка контекста чата

Сейчас чат сжимается только при смене модели (порог `providerSwitchContextTokens`, 250k), а Claude и Codex сами
сжимаются у края окна (475k). Поэтому вызов в длинном чате стоит ~230k токенов чтения кэша, а иногда 440k.

- [x] **2.0 DeepSeek: история не режется, кэш всегда промахивается (найдено 2026-11-23, исправлено в 2.0.10).** При смене Claude → DeepSeek
  чат сжал историю с 1,14M до 107k токенов, но каждый запрос пришёл в HTTP-провайдер с 4 490 сообщениями (оценка 1,7M).
  - Причина: `composite-provider.ts` отдаёт провайдеру не сообщения чата, а `ConversationHistory.begin()` →
    `mergeConversationHistory`, который восстанавливает из журнала «пропущенные рендером Copilot» сообщения и тем самым
    отменяет сжатие чата. После 2.0.8 единственный вызывающий — чат SubHarness, он шлёт полную авторитетную историю.
    Исправление: провайдер получает сообщения чата; журнал остаётся только транскриптом (`transcriptPath`, `servedBy`).
  - Провайдер сжимает каждый запрос заново: цель — 75% текущего размера (`selectContextCompaction`), а не бюджет, поэтому
    1,7M → 1,3M → 400 → 0,9M → 400 → 0,68M; три сводки DeepSeek (~95k токенов, ~35 с) на запрос, новая сводка в начале
    истории каждый раз — отсюда 0–1,2% кэша (кэшируются только системный промпт и инструменты, 8 448 токенов).
    Исправление: цель не выше `softInputTarget` (на overflow — `hardInputTarget`), сжатый снимок переиспользуется.
  - Отправлено 713k при окне 475k: overflow-ретрай целится в 75% от прошлой попытки, а реальный предел DeepSeek — 1M.
  - Первая попытка каждого запроса — 400, после которого результаты инструментов переводятся в user-сообщения
    (`isToolRoleCompatibilityError`); текст ошибки не логируется — логировать и не путать переполнение с ошибкой роли.
  - Итог (2.0.10): провайдер получает сообщения чата; цель сжатия — доля от min(размер, `softInputTarget`), и для
    overflow-ретрая тоже. Первая 400 была настоящей ошибкой роли (переполнение идёт своим ретраем раньше), скорее
    всего из-за склейки журнала: теперь текст ошибки в логе, а откат на user-результаты запоминается для чата,
    чтобы снимок совпадал (именно из-за смены формата он сбрасывался каждый запрос).
- [x] **2.1 Исследование провайдеров** (2026-11-25). Чат шлёт полную историю каждый запрос, но нативные провайдеры
  берут из неё только хвост:
  - Claude: тёплая или восстановленная сессия получает только последнее сообщение пользователя
    (`createLatestUserMessage`); изменённые старые сообщения игнорируются, сессия держит свою полную историю.
  - Codex: при том же `_conversationId` тред переиспользуется (`trustedConversation`), уходит только хвост после
    прошлого ответа.
  - Cursor и Coco: нативная сессия получает дельту с `deltaStart`.
  - HTTP (llama.cpp, DeepSeek): история уходит как есть. Сжатый снимок провайдера находит устаревание по
    выравниванию, но не всегда, поэтому при сбросе его надо удалять явно.

  Значит, очищенную историю нативный провайдер увидит, только если начнёт новую сессию. Готовый путь для этого —
  смена провайдера: `_aabProviderSwitched` (`isProviderSwitch`) уже понимают Claude, Codex, Cursor и Coco: они
  бросают живую и сохранённую сессию и начинают с replay переданной истории в пределах
  `providerSwitchContextTokens`. Оценка чата (байты/2) вдвое осторожнее оценки Claude (символы/4), поэтому
  очищенные ~120k по оценке чата помещаются в replay Claude без обрезки.

  Решение:
  - один сброс на очистку: первый запрос после неё несёт `_aabHistoryReset`, провайдеры обрабатывают его как смену
    провайдера, HTTP удаляет сжатый снимок разговора;
  - признак сброса не хранится: запрос сбрасывает сессию, пока после новейшего сжатия в истории нет ответа модели.
    Так повтор после ошибки и перезагрузка окна сбрасывают снова, а следующие раунды того же хода — нет;
  - собственное сжатие Claude и Codex у края окна остаётся страховкой. Чат о нём не узнаёт: Claude отбрасывает
    `compact_boundary`, Codex — `thread/compacted`.
- [x] **2.2 Правила устаревания результатов инструментов** (сделано в 2.0.13). Заменяются короткой пометкой (инструмент, аргументы,
  одна строка итога): чтение файла, который потом правили или перечитали; вывод терминала и проверок, после
  которых был более новый запуск; результаты поиска и списков из прошлых запросов; большие результаты старше
  K ходов. Не трогаются: сообщения пользователя, итоговые ответы агента, результаты текущего запроса и то, на что
  опирается открытый todo-план.
  Решение: пометка хранится в части `compaction` (`staleResults`, id вызовов), текст пометки строится из самого
  результата, поэтому он не меняется от запроса к запросу и не ломает кэш. Не трогаются отчёты субагентов, ответы
  на вопросы, todo и память; результаты короче 1 200 символов не заменяются. Todo-план пока не учитывается.
- [x] **2.3 Рабочий бюджет с гистерезисом** (сделано в 2.0.13). Настройка рабочего контекста (по умолчанию ~200k): когда последний
  запрос превысил бюджет, чат очищается до ~60% — сначала устаревшие результаты, затем сводка старых ходов
  (существующее сжатие). Очистка идёт на границе запросов пользователя, пачкой, чтобы кэш перестраивался один раз.
  Нативное сжатие у края окна остаётся страховкой.
  Решение: настройка `llamacpp.chatContextBudget` (токены, 0 — выключено). Размер считается в реальных токенах:
  оценка чата умножается на отношение «последний `promptTokens` провайдера / оценка». Поэтому сессия, которую
  провайдер сжал сам, очистку не запускает. Очистка меньше чем на 10% бюджета не делается: сброс стоит replay.
  Внутри одного длинного запроса чат не чистится, там страхует нативное сжатие.
- [x] **2.4 Применение к провайдерам** по итогам 2.1 (сделано в 2.0.13): `_aabHistoryReset` в `agent-loop.ts`,
  `isProviderSwitch` его учитывает, HTTP удаляет снимок (`chat.messages.snapshot_reset`). Вживую не проверено.
- [x] **2.5 Смена модели** берёт уже очищенную историю; отдельное сжатие только если она всё ещё выше порога
  (сделано в 2.0.13; сжатие при смене сохраняет пометки очистки).
- [x] **2.6 Карточка очистки** показывает, что убрано (N результатов, M ходов в сводке); полная история остаётся в
  ленте чата (сделано в 2.0.13, «Context cleaned»).
- [x] **2.7 Метрики:** размер запроса до/после очистки в логе и в Session Quality (сделано в 2.0.13:
  `chat.cleaning.done` / `skipped` / `summary_failed`; в Session Quality счётчик в Reliability и таблица
  «Chat cleanings»).
- [ ] **2.8 Проверка вживую.** Длинный чат на Claude, Codex и DeepSeek с бюджетом ~100k: очистка срабатывает,
  первый запрос после неё начинает новую сессию (`provider_switch_cold_start` с `historyReset`), следующие идут в
  неё же с кэшем. Позже: учитывать открытый todo-план; очистка внутри очень длинного запроса.
  - [x] Claude, 2026-11-25, этот чат после перезагрузки: `chat.cleaning.done` 239 517 → 120 064 токенов (scale
    0,381; 116 пометок, сводка DeepSeek за 12 с), затем `claude.chat.provider_switch_cold_start` с
    `historyReset: true`, следующие раунды — `tool_resumed` в новой сессии. Найдено: повтор ограничен
    `providerSwitchContextTokens` (~448 тыс. символов), очищенная история не влезла, и Claude отбросил 189
    старых сообщений вместе со сводкой. Исправлено: цель очистки не выше 70% этого лимита, при обрезке повтора
    сводка (`<conversation_summary>`) остаётся у Claude и в общем handoff Codex, Cursor и Coco.
  - [ ] Codex и DeepSeek.
